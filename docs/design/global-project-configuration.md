# Herta 用户级与项目级配置设计提案

## 目标

Herta 的可编辑规则与 MCP 不能再隐含地存入 Electron 的 `userData`。用户应能在文件系统中清楚看到全局配置，项目配置应始终随用户实际选择的工作区读取和写入。该设计借鉴 Claude Code 的用户—项目指令顺序与 MCP scope，以及 Codex 的 `~/.codex`—`.codex` 分层、显式项目信任和项目覆盖原则。

## 目录与职责

| 范围 | 默认目录 | 可编辑内容 | 适用范围 | 版本控制建议 |
|---|---|---|---|---|
| 用户级 | `~/.herta/`；Windows 为 `%USERPROFILE%\\.herta\\` | `mcp.json`、`rules.md`、`rules1.md`、`rules2.md` 等 | 当前用户打开的全部工作区 | 私有，不纳入项目仓库 |
| 项目级 | `<有效工作区>/.herta/` | `mcp.json`、`rules.md`、`rules1.md`、`rules2.md` 等 | 当前工作区及其新建/重开会话 | 由用户决定；含密钥时应忽略，团队共享时应使用环境变量而非明文密钥 |
| 应用私有状态 | Electron `userData` 和 OS 安全存储 | 窗口状态、主题、语言、更新状态、加密 API Key、会话元数据 | 当前机器与当前应用安装 | 不作为用户配置目录，也不作为规则/MCP 配置来源 |

`HERTA_HOME` 环境变量应允许用户覆盖 `~/.herta/`，以便将全局配置迁移到自定义磁盘、便携盘或组织托管目录。它只改变用户级规则/MCP 配置根，不改变 Electron 机器状态或安全存储。

## 规则加载与优先级

每次请求均重新读取规则，使保存后下一轮生效。每层仍只发现 `rules.md`、`rules1.md`、`rules2.md` 等严格匹配 `^rules\d*\.md$` 的文件；层内按未编号文件、再按数字编号的顺序加载。

规则文本按下列顺序拼接：用户级规则在前，项目级规则在后。因为项目规则在后进入模型上下文，所以当两者发生冲突时，项目规则具有局部优先级。两层都同时注入黑塔与板砖的独立上下文，不能只注入其中一方。

为便于诊断，运行时应在会话启动或 `/context` 等查看界面中显示本轮实际加载的规则文件及其 scope；不展示规则正文以避免额外泄露。

## MCP 加载与优先级

会话启动时分别读取 `~/.herta/mcp.json` 与 `<工作区>/.herta/mcp.json`。服务器按名称合并：先加载用户级服务器，再加载项目级服务器；项目级同名条目完整替换用户级条目。不同名称的条目同时可用。

这意味着用户可在全局配置中放置经常使用的浏览器、文档或代码搜索 MCP；项目可以只添加该项目特有的数据库或部署服务，也可以用同名服务器覆盖全局地址、参数或环境变量。MCP 配置保存后只对新建或重新打开的会话生效，因为已有会话已经拥有连接的工具客户端。

项目 MCP 具有执行本地命令或发送网络请求的能力。若项目目录来自仓库克隆或尚未被用户信任，Herta 应明确显示项目范围配置来源并要求用户首次确认启用项目 MCP；用户级 MCP 不需要每个项目重复确认。

## GUI 交互

MCP 服务和项目规则设置页均使用同一种明确的范围切换器：**全局（所有工作区）**与**项目（当前工作区）**。页面顶部应始终显示真实绝对路径，例如：

```text
全局：C:\\Users\\Alice\\.herta\\mcp.json
项目：D:\\迅雷下载\\nex\\herta\\.herta\\mcp.json
```

项目范围仅在存在活动会话或已明确选择有效工作区时可编辑；没有项目上下文时，控件应禁用并解释原因，绝不能回退写入 Electron `userData`。保存后必须显示“已保存到 `<绝对路径>`”。联合视图可显示来自全局和项目的服务器，并标记“由项目配置覆盖”。

规则页面的“新建规则”仅在用户点击并保存时创建文件；不会因为升级或打开设置而制造空的 `rules.md`。同一页面应在两个 scope 中分别管理各自的规则文件。

## 迁移与兼容

现有版本错误地将 GUI MCP 保存到 Electron `userData/.herta/mcp.json`，同时会话也从该目录读取。升级到新设计后，应用应检测此旧文件，并在首次使用 MCP 设置时显示一次迁移提示：

> 发现旧版 Herta MCP 配置。是否复制到用户级配置 `~/.herta/mcp.json`？

默认操作应是“复制并保留旧文件”，而不是无提示移动或删除，因为 MCP 条目可能含私密 Header。用户可选择跳过，或随后通过 GUI 的“迁移旧配置”按钮处理。项目级文件绝不自动从旧配置生成；用户需要在项目页明确保存，防止一个全局配置被意外复制进多个仓库。

旧版 Electron `userData/.herta/mcp.json` 仅作为一次性迁移来源；迁移后不再参与正常合并或会话启动读取，避免同一服务器出现不透明的第三来源。

## 实施验收条件

| 场景 | 预期结果 |
|---|---|
| 在全局 MCP 页新增服务 | 仅创建/更新 `~/.herta/mcp.json`；任何工作区的新会话可用。 |
| 在 `D:\\project` 的项目 MCP 页新增服务 | 仅创建/更新 `D:\\project\\.herta\\mcp.json`；不影响其他项目。 |
| 全局和项目均有同名服务 | 新会话使用项目版本；GUI 联合视图明确显示覆盖。 |
| 全局和项目均有规则 | 黑塔与板砖都获得“全局在前、项目在后”的相同规则组合。 |
| 无活动项目时打开项目范围设置 | 不写任何文件；提示选择或创建工作区。 |
| 旧版用户数据目录中存在 MCP 配置 | 有明确、可拒绝的一次性复制迁移；不静默删除。 |
